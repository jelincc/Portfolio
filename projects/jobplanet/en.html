Hypothesis

If Home is rebuilt around search + contextual modules

We validated the two hypotheses below directly using this prototype

Our initial hypothesis was that building Home around job-function-based recommended content would keep users exploring there — so we built it into real screens (a radar chart, followed-company content, and more) and validated it through integrated UT.

The result was close to a total miss, and using that UT data as evidence, we rebuilt the hypothesis around a search-first + contextual-module structure.

Decisions

Search-Bar-Centric + State-Based Modularity

Core Shift
AS-IS

Home = a space that lists content

TO-BE

Home = a search + context hub. The search bar is the primary entry point, with modules underneath that shift based on user state.

Search Bar (Fixed): Top priority at the top of Home. Marks the clear starting point for exploration.

Followed-Company Closing Soon (Module A): Shown when the user follows companies. A repeat-visit trigger. Carousel on PC; condensed to a banner on mobile to account for scroll depth.

Past/Current Employer Review Feed (Module B): A module built to increase review consumption.

Review-Themed Listings (Module C): Review-driven curation like "can leave on time" or "generous budget."

Decisions We Shelved: Based on UT Data

Radar chart personalization: 4/7 failed to grasp its meaning, adding cognitive load with nothing to show for it

"Recently viewed companies" side widget: broke the browsing flow, and demand was low

Generic job-function-based recommendations: the "companies I don't know" direction simply didn't work

Decisions and Trade-offs

01Narrowed personalization scope to "followed-company updates"
RiskNew or logged-out users with no followed companies never see the module at all, so the cold start problem isn't solved — it's just avoided.
ResponsePlan to cover this user group with a second round of UT on contextual content placement when entering GNB tabs (Next Steps 01, see Appendix).
02Fixed the top of Home to the search bar
RiskSearch proved a strong lever toward reviews (2.8x on PC, up to 6.6x on iOS), but the lever toward listings varied by device, so it only indirectly serves our original goal of improving the hiring funnel.
ResponseLeft resolving the review-to-listing conversion bottleneck as a next step (Next Steps 02, see Appendix).
03Made the repeat-visit trigger depend on the followed-company module
RiskCompany-follow creation itself dropped -10% after launch, shaking the very baseline the module depends on.
ResponseContinuing to monitor the follow-creation trend (Next Steps 03, see Appendix).
04Kept GNB as a destination shortcut, shelved a redesign
RiskIts role in the exploration flow remains Not validated, so the benefit of improving exploration through GNB hasn't been proven yet.
ResponseMade explicit that turning GNB into an exploration tool requires contextual content on tab entry as a precondition, and it's under further review.
Final Design

Real Screens Built From UT Hypotheses

Breaking down the shipped Home screen top to bottom, each module centers on core functionality meant to drive review and listing views. We built it in a modular form so admins can directly control whether and in what order each module appears.

Reinforcing an already-familiar search flow

We made the search bar the backbone of Home, foregrounding it centrally to increase the search attempt rate.

Gathering scattered menus into a quick menu

We gathered features that had been dropped from GNB, or that already had high click-through, into a quick menu to boost accessibility.

Closing-soon listings banner

We added closing-soon listings — the only thing in UT that drove voluntary repeat visits — as a strip banner, sized with mobile scroll depth in mind.

#Keyword-Mentioned Top Companies

We added a review curation module to drive reach toward reviews, one of the service's core functions.

In A/B testing, the review-forward card won by up to 73% on click-through, so we went with Review Card A. (Shown conditionally based on login status, follows, and whether a listing closes within D-7)

Review-based recommended listings

We added a module that groups listings by review-derived theme, guiding users toward both reviews and listings together.

We consolidated 12 overlapping themes down into a new set of theme cards.

What We Learned

What moved users wasn't "personalization" — it was review browsing.

The review curation module's CTR outperformed the listing module, and the new Company Reviews tab logged higher usage than the existing Job Listings tab.

About 76.8% of search users checked reviews first, meaning search functioned as the key entry point into review browsing.

Key Insight

Users were more engaged when they could quickly check reviews for companies they already cared about, rather than being recommended something new.

→ Review curation and search-first UX reinforced this behavior pattern, and that fed directly into improvements in the product's core metrics.

The Hypothesis Redefinition Was Right: Just as UT had confirmed — "generic personalization fails, only contextual personalization (followed-company updates) works" — after launch too, connections to information users already knew (reviews) drove real clicks, not unfamiliar recommendations.

The execution of the hypothesis (which modules, exactly) kept needing refinement even after UT, but the judgment call on "what actually moves users" had already been right at the UT stage.

A later causal analysis, run through a placebo test, confirmed that users exposed to the review feed showed a net increase of +2.5 to 3.1 review views per day — giving this judgment statistical backing as well.

Appendix 3 · Module Policy Shared Document for Planning & Engineering

Defining the Rules for Module Combinations, So Engineering and I Could Read From the Same Document

Once Home was broken down into modules, there was no clear rule for "which combinations are actually valid." We split modules along two axes — behavior type and content type — and mapped only the combinations actually in use into a matrix.

Values that change often, like item count, were left as variables, and we built a registry for client and server engineers to fill in directly — code name, API endpoint, in-use status. The key was getting planning and engineering to work from one single document.

Why This Was Needed: When teams call the same module by different names, communication tangles easily — and if that confusion repeats, it wastes not just communication overhead but engineering effort spent building in the wrong direction.

If server query conditions, sort order, and item count match, and the display method per platform matches, it's the same module. If only visual elements like background color differ, it's a variation.

This single standard gave us a shared language for calling the same thing by the same name.

Appendix 4 · Design System Unified Across Web · iOS · Android · Mobile Web

Unifying Components That Had Diverged Across Platforms Into JDS 1.0

Before the Home redesign, basic components like buttons, cards, and badges were each defined separately across web, iOS, Android, and mobile web. While doing the modularization work, I decided this problem couldn't be put off any longer, so I built JDS 1.0, a cross-platform component system.

Core Shift
AS-IS

Even for the same "card," web, iOS, Android, and mobile web each defined spacing, color, and states separately. Fixing one thing meant touching four places separately.

TO-BE

Color, typography, spacing, and component specs defined once as platform-agnostic tokens. Web, iOS, Android, and mobile web all reference the same values.

01Spacing, color, and state handling differed by platform
ProblemEven the same "card" component had slightly different values across web, iOS, Android, and mobile web, and no one was confident which one was the correct reference.
SolutionDefined color, typography, and spacing as platform-agnostic tokens so all four platforms reference the same values.
02One fix required touching all four platforms separately
ProblemFixing even a single button meant editing web, iOS, Android, and mobile web separately, hurting both rollout speed and consistency.
SolutionConsolidated basic components — buttons, cards, badges, inputs — into a single spec with no per-platform variation.
03Teams called components by different names
ProblemPlanning, design, and engineering called the same element by different names, so everyone pictured something different in every discussion.
SolutionDocumented component names, states, and usage conditions the same way as the module policy document.
